# 1. PROJECT OVERVIEW

- **Project Name**: FitTrack (FitTrack Premium / FitTrack AI)
- **One-Line Description**: A full-stack MERN (MongoDB, Express, React, Node.js) fitness and nutrition tracking web application powered by Google Gemini 2.0 Flash AI for structured workout plan generation, diet planning, and real-time food nutrition estimation.
- **Detailed Description**: FitTrack delivers personalized workout routines and meal plans tailored to individual biometric profiles, fitness goals, dietary preferences, and training locations. Unlike traditional chatbots that return unstructured text, FitTrack integrates Google Gemini AI with native JSON schema enforcement to generate structured MongoDB documents directly. It includes a user dashboard with streak calculation, 7-day caloric performance charting, interactive workout/food logging with AI estimation, BMI tracking, and Google OAuth 2.0 authentication.
- **Main Purpose / Problem Solved**: Eliminates generic, one-size-fits-all fitness templates and tedious manual nutrition entry by leveraging AI to generate customized 7-day training and meal roadmaps and auto-estimating meal caloric/macronutrient values.
- **Target Users**: Fitness enthusiasts, gym-goers, home workout individuals, and people seeking personalized dietary and exercise planning.
- **Main Use Cases**:
  1. User signup/login or Google OAuth 2.0 authentication.
  2. Biometric onboarding (capturing age, weight, height, goal, diet type, activity level, workout location).
  3. Generating personalized 7-day AI workout programs tailored to goals (e.g., hypertrophy, fat loss, flexibility, endurance).
  4. Generating personalized 7-day AI meal plans with macro breakdowns and daily calorie targets.
  5. Logging completed workouts (exercise, sets, reps, weight) and food items with real-time AI calorie & macro estimation.
  6. Monitoring fitness progress, streak count, BMI status, and 7-day calorie consumption charts on the dashboard.
- **Current Project Status**: Production Ready / Fully Functional Core. Deployed/Deployable on Render (Backend) and Vercel (Frontend).
- **Overall Architecture**: Client-Server SPA Architecture.
  - **Frontend**: React 19 SPA built with Vite, styled using Tailwind CSS and Framer Motion, with React Router v7.
  - **Backend**: Node.js & Express RESTful API with JWT authentication and Passport.js Google OAuth 2.0.
  - **Database**: MongoDB (via Mongoose ODM) with Connect-Mongo session storage.
  - **AI Engine**: Google Gen AI (`@google/genai`) utilizing `gemini-3.7-flash` (primary), `gemini-3.5-flash` (fallback), and `gemini-3.5-flash-lite` (lookup) with native JSON schema enforcement.
- **Major Technologies Used**: Node.js, Express, React 19, Vite, MongoDB, Mongoose, JWT, Passport.js, Google Gemini API, Tailwind CSS, Framer Motion, Recharts, Lucide React, Axios.

## Key File Details

### `server/server.js`
- **Purpose**: Entry point for backend API server.
- **Responsibilities**: Loads environment variables, connects to MongoDB, sets up CORS rules, configures session storage with `connect-mongo`, initializes Passport.js, registers API route handlers, serves static client build in production (`client/dist`), and attaches global error handlers.
- **Important Functions**: `app.listen()`, `app.use()`.
- **Inputs**: Incoming HTTP requests.
- **Outputs**: HTTP responses / static files.
- **Dependencies**: `express`, `cors`, `express-session`, `passport`, `connect-mongo`, `./config/db`, `./middleware/errorMiddleware`.
- **Used by**: Node runtime (`node server.js`).
- **Calls**: `connectDB()`, Passport routes, sub-routers (`authRoutes`, `userRoutes`, `workoutRoutes`, `dietRoutes`, `trackerRoutes`, `dashboardRoutes`).

### `server/config/passport.js`
- **Purpose**: Google OAuth 2.0 authentication strategy.
- **Responsibilities**: Verifies Google OAuth user profiles. Finds user by `googleId` or matching `email`. If user exists with email, links `googleId`; if brand new, creates user record without password. Performs minimal serialization (`user.id`).
- **Used by**: `server.js`, `authRoutes.js`.

### `server/services/aiService.js`
- **Purpose**: Centralized Gemini AI generation service with resilient retry, deadline management, and multi-model failover.
- **Responsibilities**:
  - Enforces shared total deadlines (30s for workout/diet plans, 10s for nutrition lookup) and per-attempt timeouts (15s for plans, 6s for lookup) using `Promise.race`.
  - Integrates 30-day `NutritionCache` for food lookups: normalizes queries (NFKC, lowercase, trim, collapse spaces, strip trailing punctuation), queries cache before calling Gemini, and upserts valid AI results (calories <= 5000). Returns `source: "cache"` or `source: "ai"`.
  - Primary model: `process.env.GEMINI_MODEL || 'gemini-3.5-flash-lite'`; lookup model: `process.env.GEMINI_LOOKUP_MODEL || 'gemini-3.5-flash-lite'`; fallback model: `process.env.GEMINI_FALLBACK_MODEL || null`.
  - On 503 / timeout: retries the same model once after a jittered 1-3s delay if the deadline budget allows, then falls back to `GEMINI_FALLBACK_MODEL`.
  - On 429 quota: switches immediately to fallback model.
  - On 400 thinkingConfig rejection: retries immediately without `thinkingConfig` on the same model.
  - On 404: logs critical error for missing/deprecated model.
  - Logs model and attempt serving each request. Preserves 1 decimal place on macros and runs soft macro-calorie sanity check.
- **Used by**: `workoutController.js`, `dietController.js`.

### `server/models/NutritionCache.js`
- **Purpose**: MongoDB collection storing AI-estimated food nutrition lookups with a 30-day TTL index.
- **Responsibilities**:
  - `key`: Normalized query string (NFKC, lowercase, trimmed, collapsed whitespace, trailing punctuation stripped) with unique index.
  - `result`: `{ name, calories, protein, carbs, fats }`.
  - `createdAt`: Date field with MongoDB TTL index set to 30 days (`2592000` seconds).
  - Never stores user PII or user IDs. Does not cache `COULD_NOT_ESTIMATE` failures or >5000 kcal items.
- **Used by**: `aiService.js`.

### `server/controllers/workoutController.js`
- **Purpose**: Handles AI workout generation and workout logging.
- **Responsibilities**: Delegates plan generation to `aiService.generateWorkoutPlan({ goal, fitnessLevel })`. Creates `Workout` document. Maps AI errors to HTTP 502 with friendly user messaging (400 on safety blocks). Also creates `WorkoutLog` entries and fetches exercise suggestions.
- **Important Functions**: `generateWorkout`, `getWorkoutHistory`, `logWorkout`, `getRecentExercises`, `deleteWorkout`.
- **Used by**: `workoutRoutes.js`.
- **Calls**: `aiService.generateWorkoutPlan()`, `Workout.create()`, `WorkoutLog.create()`, `Workout.find()`.

### `server/controllers/dietController.js`
- **Purpose**: Handles AI daily nutrition blueprint generation, food logging, and AI nutrition estimations.
- **Responsibilities**: Delegates blueprint generation to `aiService.generateDietPlan({ goal, dietType })` and food lookups to `aiService.lookupNutrition(query)`. Maps AI errors to HTTP 502 with friendly user messaging (400 on safety blocks). Logs food to `DietLog`.
- **Important Functions**: `generateDiet`, `getDietHistory`, `logDiet`, `getRecentFoods`, `lookupNutrition`.
- **Used by**: `dietRoutes.js`.
- **Calls**: `aiService.generateDietPlan()`, `aiService.lookupNutrition()`, `Diet.create()`, `DietLog.create()`, `DietLog.find()`.

### `client/src/services/api.js`
- **Purpose**: Centralized Axios HTTP client.
- **Responsibilities**: Attaches Bearer JWT token from `localStorage` (`fittrack_token`) to request headers. Handles `401 Unauthorized` responses by clearing local storage and redirecting to `/login`. Exports API wrapper modules (`authAPI`, `userAPI`, `workoutAPI`, `dietAPI`, `trackerAPI`, `dashboardAPI`).
- **Used by**: All page components and context providers (`AuthContext`, `Dashboard`, `Diet`, `Workout`, `Tracker`, `Profile`, `LogFoodModal`, `LogWorkoutModal`).

## Communication & Execution Flows

1. **Request Flow**: Client sends request via `api.js` Axios instance → Request Interceptor attaches `Authorization: Bearer <JWT_TOKEN>` → Express server receives request → CORS middleware checks origin → Route handler matches path → `authMiddleware.protect` verifies JWT and attaches user object (`req.user`) → Controller executes business logic.
2. **Response Flow**: Controller executes query/AI call → Formats JSON payload → Sends HTTP status (200, 201, 400, 401, 500) with JSON body → Client Axios response interceptor receives data → React state updates → UI re-renders.
3. **Authentication Flow**:
   - **Local Auth**: User posts email/password → `authController.login` verifies bcrypt hash → Returns JWT token & user profile object → Client saves token in `localStorage` & `AuthContext`.
   - **OAuth**: User clicks "Google Login" → Redirected to `/api/auth/google` → Passport handles Google consent → Google redirects to `/api/auth/google/callback` → Passport finds/creates user → Express generates JWT token → Server redirects client to `/oauth-callback?token=<JWT_TOKEN>` → `OAuthCallback.jsx` reads URL query, stores token, fetches profile, and redirects user.
4. **Database Flow**: Mongoose models (`User`, `Workout`, `Diet`, `WorkoutLog`, `DietLog`, `Log`) connect via `server/config/db.js` using URI `process.env.MONGO_URI`. Session persistence during OAuth uses `connect-mongo`.
5. **External API Flow (AI)**: `workoutController` / `dietController` / `lookupNutrition` construct prompts with strict JSON schema instructions → Call `genAI.getGenerativeModel({ model: "gemini-2.0-flash", systemInstruction: ... })` → Response returned as raw text → Processed through `cleanAIJSON()` → Parsed via `JSON.parse()` → Stored in MongoDB → Returned to client.
6. **Error Flow**: Errors inside controllers are caught via `try/catch` blocks → Passed to Express `res.status(statusCode).json({ message })` or `next(error)` → Handled by `errorMiddleware.js` (`notFound` / `errorHandler`).

# 6. COMPLETE APPLICATION FLOW

1. **Application Initialization**:
   - User loads application (`/`). `App.jsx` mounts `AuthProvider` and `ThemeProvider`.
   - `AuthProvider` reads `fittrack_token` and `fittrack_user` from `localStorage`.
2. **Public Browsing / Authentication**:
   - User visits Landing Page (`/`).
   - Clicking "Sign In" or "Get Started" navigates to `/login` or `/signup`.
   - User authenticates via email/password or Google OAuth.
3. **Onboarding Check Guard**:
   - `ProtectedRoute` inspects `user.isOnboarded`.
   - If user is not onboarded (`isOnboarded: false`), user is forcibly redirected to `/app/onboarding`.
   - Onboarding collects age, weight, height, goal, diet type, activity level, and workout location.
   - Submitting updates profile via `userAPI.updateProfile`, setting `isOnboarded: true`.
4. **Dashboard View (`/app/dashboard`)**:
   - Fetches summary statistics from `dashboardAPI.getSummary()`.
   - Renders 7-day caloric performance bar chart (`Recharts`), workout streak badge, current active AI workout program, current AI meal plan, and recent activity log feed.
5. **Generating & Managing Workouts (`/app/workout`)**:
   - User clicks "Generate AI Workout". Selects target fitness goal and experience level.
   - Backend queries Gemini 2.0 Flash → Returns structured 7-day workout plan → Saved to MongoDB → Displayed in interactive day accordion tabs.
   - User clicks "Log Exercise" → Opens `LogWorkoutModal` → Submits exercise details → Saved to `WorkoutLog` → Refreshes dashboard & tracker.
6. **Generating & Managing Diets (`/app/diet`)**:
   - User clicks "Generate AI Meal Plan". Selects diet preference (e.g. Vegetarian, High Protein).
   - Backend queries Gemini 2.0 Flash → Returns 7-day meal plan with daily target calories and macro split (Protein, Carbs, Fats) → Saved to MongoDB.
   - User logs food via `LogFoodModal` → Types food name (e.g., "2 Boiled Eggs") → Debounced AI call triggers `dietAPI.lookup` → Gemini auto-populates estimated calories and macros → User saves log.
7. **Progress Tracking (`/app/tracker`)**:
   - User views overall stats (`trackerAPI.getStats()`): BMI value, WHO BMI classification badge (Underweight, Healthy, Overweight, Obese), total workouts completed, daily calories logged.
   - Filters activity feed by All, Workouts, or Diet logs.
8. **Profile & Account Management (`/app/profile`)**:
   - User views and updates biometric parameters, changes fitness goals, or deletes account.

# 7. FEATURE DOCUMENTATION

## Feature 1: AI Workout Plan Generator

### Purpose
Generates a structured 7-day training schedule customized to user biometrics, fitness level, and training goals.

### User Flow
User navigates to `/app/workout` → Clicks "Generate Plan" → Chooses goal/level → Submits → Loading state displays → AI returns structured plan → Rendered in tabs.

### Frontend
- **Page**: `client/src/pages/Workout.jsx`
- **Components**: `Card`, `Button`, `Select`, `LogWorkoutModal`.
- **API Call**: `workoutAPI.generate({ goal, fitnessLevel })`.

### Backend
- **Route**: `POST /api/workout/generate` (Protected, rate limited: 10/15min per user, 5xx/429 exempted)
- **Controller**: `workoutController.generateWorkout`
- **Logic**: Delegates to `aiService.generateWorkoutPlan` with shared 30s deadline (15s per-attempt timeout). Uses `gemini-3.5-flash-lite` (primary) and optional `GEMINI_FALLBACK_MODEL`. Retries 503 once with 1-3s jitter; falls back immediately on 429; retries without thinkingConfig on 400. Saves plan object to `Workout` collection.

### Database
- **Collection**: `workouts`
- **Fields**: `userId` (ObjectId ref User), `plan` (Object containing `title`, `overview`, `days` array of 7 days).

### External Services
- **Google Gemini API**: `@google/genai` with model `gemini-3.5-flash-lite`.

### Data Flow
Frontend Form → `workoutAPI.generate()` → `POST /api/workout/generate` → `authMiddleware.protect` → `aiGenerateLimiter` → `workoutController.generateWorkout` → `aiService.generateWorkoutPlan` → Gemini API → Parsed JSON → `Workout.create()` → Responded to client → React State update.

### Error Handling
If Gemini fails, returns HTTP 502 with friendly user message: `"AI Coach is currently experiencing high demand. Please try again in a few moments."` Safety blocks return HTTP 400.

## Feature 2: AI Daily Nutrition Blueprint & AI Nutrition Lookup

### Purpose
Generates personalized daily nutrition blueprints (target calories, macro splits, and meal suggestions across 4 categories) and offers sub-second AI estimations of calories and macros for arbitrary food items.

### User Flow
1. **Daily Blueprint**: User goes to `/app/diet` → Selects diet preference & goal → Clicks "Generate Blueprint" → `aiService` returns daily blueprint with macro profile → Stored in MongoDB and displayed.
2. **AI Nutrition Lookup**: User opens `LogFoodModal` → Types food name and weight/quantity → Debounced AI call estimates calories and macros (1 decimal precision) → Auto-populates input fields.

### Frontend
- **Pages / Modals**: `client/src/pages/Diet.jsx`, `client/src/components/modals/LogFoodModal.jsx`.
- **API Calls**: `dietAPI.generate()`, `dietAPI.lookup(query)`, `dietAPI.log(formData)`.

### Backend
- **Routes**: `POST /api/diet/generate` (Protected, rate limited: 10/15min), `GET /api/diet/lookup` (Protected, rate limited: 60/15min, 5xx/429 exempted), `POST /api/diet/log`.
- **Controller**: `dietController.js` (`generateDiet`, `lookupNutrition`, `logDiet`).

# 12. AUTHENTICATION & AUTHORIZATION

- **Password Hashing**: `bcryptjs` with 10 salt rounds executed in `UserSchema.pre('save')` hook.
- **JWT Tokens**: Signed using `jwt.sign({ id }, process.env.JWT_SECRET, { expiresIn: '30d' })`.
- **Google OAuth 2.0 (Secure Code Exchange Flow)**: Implemented via Passport.js (`passport-google-oauth20`).
  - Google Client ID & Secret configured in `server/.env`.
  - Callback URL: `/api/auth/google/callback`.
  - Express Session enabled via `connect-mongo` during OAuth handshake.
  - On callback success, backend generates a cryptographically random 32-byte authorization code, stores its SHA-256 hash in `OAuthCode` (with 60-second TTL index), and redirects user to `${CLIENT_URL}/oauth-callback?code=${rawCode}` (no tokens exposed in URL).
  - Frontend `OAuthCallback` page calls `POST /api/auth/oauth/exchange` with `{ code }`.
  - Backend performs atomic, single-use redemption via `OAuthCode.findOneAndDelete({ codeHash })`, retrieves user, issues JWT, and returns user object with `isOnboarded` status.

# 18. IMPORTANT BUSINESS LOGIC

1. **BMI Calculation**:
   $$\text{BMI} = \frac{\text{weight (kg)}}{(\text{height (m)})^2}$$
   - Status boundaries: `< 18.5`: Underweight | `18.5 - 24.9`: Healthy | `25.0 - 29.9`: Overweight | `>= 30.0`: Obese.
2. **Calorie & Macro Target Calculation (Mifflin-St Jeor)**:
   - **Basal Metabolic Rate (BMR)**:
     $$\text{BMR} = (10 \times \text{weight in kg}) + (6.25 \times \text{height in cm}) - (5 \times \text{age}) + s$$
     where $s = +5$ for male, $s = -161$ for female, and $s = -78$ for unspecified or missing sex (midpoint midpoint constant between male and female).
   - **Total Daily Energy Expenditure (TDEE)**:
     BMR multiplied by activity multiplier (`1.2` for sedentary, `1.375` for light, `1.55` for moderate, `1.725` for active, `1.9` for very_active).
   - **Goal Adjustment**:
     - `fat_loss` / `lose_weight`: TDEE - 500 kcal
     - `muscle_gain`: TDEE + 300 kcal
     - `maintain` / `body_recomposition` / `strength` / `endurance` / `general_fitness` / `flexibility`: TDEE + 0 kcal
   - Calories clamped between `1200 kcal` (min) and `5000 kcal` (max).
   - Macro splits calculated:
     - Protein: 2.0g/kg for fat loss/muscle gain, 1.8g/kg for recomposition/strength/endurance, 1.6g/kg default.
     - Fats: 25% of total calories (9 kcal/g).
     - Carbs: Remainder calories / 4 (min 50g).
3. **Streak Calculation**: Counts distinct consecutive calendar days with logged workouts in user's time zone (`X-Timezone` header).
4. **Calorie Performance Aggregation**: Groups trailing 7 days of diet logs in user's time zone for performance charts.

### Rate Limiter Configuration Summary
- **Outer Total Rate Limiters** (Env configurable): `AI_GENERATE_TOTAL_LIMIT_PER_HOUR` (default `30`/hr) & `AI_LOOKUP_TOTAL_LIMIT_PER_HOUR` (default `300`/hr).
- **Phase 1 Success Rate Limiters** (Fixed in code): `aiGenerateLimiter` (max `10` successful plan generations per 15 min per user; `skipFailedRequests: true`) & `dietLookupLimiter` (max `60` successful nutrition lookups per 15 min per user; `skipFailedRequests: true`).
- **General API Limiter**: `apiLimiter` (max `200` requests per 15 min per IP).

### Domain & Cross-Origin Authorization Architecture
- Frontend client host (e.g. Vercel `https://fittrack.vercel.app`) sets `VITE_API_URL` targeting backend server (e.g. Render `https://fittrack-backend.onrender.com/api`).
- Backend server host sets `CLIENT_URL` targeting the frontend client URL.
- CORS middleware in `server.js` includes `CLIENT_URL` in its origin allowlist.
- Post-OAuth authentication in `authController.js` redirects browser to `${CLIENT_URL}/oauth-callback?code=${rawCode}`.
- Single-domain hosting is **NOT** required for OAuth or CORS. Backend and frontend run cleanly on distinct domains.

Follow this exact sequence during deployment:

```
(a) MONGODUMP BACKUP
    └── Run mongodump against the production database to create a complete restore point before executing scripts.

(b) SET ENVIRONMENT VARIABLES ON RENDER AND VERCEL
    └── Configure environment variables on Render (backend server) and Vercel (frontend client):
        - Render: MONGO_URI, JWT_SECRET, SESSION_SECRET, GEMINI_API_KEY, GEMINI_MODEL=gemini-3.5-flash-lite, GEMINI_LOOKUP_MODEL=gemini-3.5-flash-lite, GEMINI_FALLBACK_MODEL=gemini-3.1-flash-lite, AI_GENERATE_TOTAL_LIMIT_PER_HOUR=30, AI_LOOKUP_TOTAL_LIMIT_PER_HOUR=300, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_CALLBACK_URL, CLIENT_URL=https://fittrack.vercel.app.
        - Vercel: VITE_API_URL=https://fittrack-backend.onrender.com/api.

(c) DEPLOY SERVER AND CLIENT TOGETHER
    └── Deploy backend server and frontend client simultaneously.

(d) SMOKE TEST CRITICAL USER FLOWS
    └── Perform smoke tests in production:
        1. Password login & signup
        2. Google OAuth SSO login flow
        3. AI Workout & Diet plan generation
        4. Food logging and nutrition lookup

(e) RUN MIGRATION SCRIPTS FROM LOCALHOST
    └── Execute migration scripts sequentially from localhost (pointing MONGO_URI to production):
        1. node scripts/normalize-enums.js --execute
           (Converts legacy user document enum values e.g. 'lose_weight' -> 'fat_loss', 'Home' -> 'home')
        2. node scripts/migrate-legacy-logs.js --execute
           (Copies legacy Log records into WorkoutLog and DietLog without deleting legacy documents)

(f) TIGHTEN SCHEMA ENUMS (FUTURE RELEASE)
    └── Only after verifying migration success and data integrity, tighten Mongoose schema enum validators to reject non-canonical values in a future release.
```

## 3. Query Setters (`runSettersOnQuery`) & Endpoint Validator Audit

### Query Setter Casting Behavior (`runSettersOnQuery: true`)
- Setting `schema.set('runSettersOnQuery', true)` on the `User` schema ensures Mongoose update queries (`User.updateOne()`, `User.findOneAndUpdate()`, `User.updateMany()`) execute path setters (`normalizeGoal`, `normalizeDietType`, `normalizeWorkoutLocation`).
- Tested without a live database via Mongoose update query compilation (`_castUpdate`): update operations containing `{ $set: { goal: 'lose_weight', dietType: 'Veg', workoutLocation: 'Home' } }` automatically cast input values to canonical `'fat_loss'`, `'vegetarian'`, and `'home'`.

### Endpoint Audit for Enum Writes
All endpoints writing `workoutLocation`, `dietType`, or `goal` pass through Zod validation schemas (`validators/schemas.js`) prior to controller execution:
1. `PUT /api/user/profile` (Profile update / Onboarding):
   - Writes: `goal`, `dietType`, `workoutLocation` to `User` document.
   - Validator: `validate(updateProfileSchema)`.
   - Result: Validated & transformed via `normalizeGoal`, `normalizeDietType`, `normalizeWorkoutLocation`.
2. `POST /api/workout/generate` (AI Workout Generation):
   - Accepts: `fitnessGoal` (alias for `goal`), `workoutLocation`.
   - Validator: `validate(generateWorkoutSchema)`.
   - Result: Validated & transformed via `normalizeGoal`, `normalizeWorkoutLocation`.
3. `POST /api/diet/generate` (AI Diet Generation):
   - Accepts: `dietType`.
   - Validator: `validate(generateDietSchema)`.
   - Result: Validated & transformed via `normalizeDietType`.
4. `POST /api/auth/signup` (User Registration):
   - Accepts: `name`, `email`, `password`.
   - Validator: `validate(signupSchema)`.
   - Result: Initializes User document with default schema fields (executing model setters).
